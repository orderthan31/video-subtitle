실행일: 2026-09-11. 구현 커밋 `346ee9f` 기준으로 실제 브라우저 UI와 로컬 FastAPI를 연결했다.

## 환경 및 데이터

- Worker는 실행하지 않았다. AI 호출, 번역, 인코딩, 결과 다운로드 성공을 증명하는 테스트가 아니다.
- 기존 7.17초 합성 MP4에 유효한 `free` 박스를 붙인 67,879,425바이트 파일 사용. 대용량 실제 영상 대신 업로드 동작을 검증하는 패딩 파일이다.
- 로컬 fixture: `data/browser-fixtures/d07e6c6acb614ef8865ce09bffc41298/fixture.json` (Git 제외).
- 원본 SHA-256: `d41055241748b06f949072072410ccab08deada3a8b85615202e1df2598971fc`.

## 확인한 시나리오

1. API로 최초 4,194,304바이트를 저장한 작업 `fa644a5bf1db42ff9656e88be9fcd41b`을 준비했다.
2. 브라우저 작업 행에서 재개를 선택하고, 이름·크기가 같지만 저장된 부분의 내용이 다른 파일을 선택했다. 내용 불일치 오류가 표시되고 업로드가 중단됐다.
3. 원본 파일로 변경하고 재개했다. UI가 처리 대기로 바뀌었고 서버 파일 크기 및 전체 SHA-256이 원본과 일치했다.
4. 완료 필터는 대기 작업을 숨겼다. 진행 중 필터로 돌아와 취소했고, 전체 필터에서 취소됨 상태를 확인했다.
5. 삭제 확인 대화상자로 삭제했다. 서버 작업 폴더가 실제로 사라진 것을 확인했다.
6. 브라우저에서 새 업로드 `a113b80d5a324db480983d20a538e131`을 시작하고 일시정지를 눌렀다. 서버에 4,194,304바이트가 보존됐다.
7. 페이지를 새로고침하고 작업을 다시 선택한 뒤 원본 파일을 재선택해 재개했다. 처리 대기 상태와 전체 SHA-256 일치를 다시 확인했다.
8. 데스크톱 스크린샷에서 업로드 영역, 옵션, 작업 행의 겹침 없는 표시를 확인했다.

## 재현

별도 포트 API에 `VIDEO_STORAGE_ROOT=data/browser-test-jobs`, `WEB_CORS_ORIGINS=http://127.0.0.1:5174`를 지정한다. 웹에는 `VITE_API_BASE_URL=http://127.0.0.1:8001/api`를 지정한다.

```powershell
python scripts/browser-upload-fixture.py --source <3MB-미만의-테스트.mp4> --api http://127.0.0.1:8001/api
```

출력된 원본·변조 파일 경로로 위 브라우저 시나리오를 수행한다. 스크립트는 테스트 작업을 생성하고 최초 4MB를 실제 전송하므로 격리 저장소에 연결한다. 새 실행은 고유 폴더를 만들며 기존 파일을 덮어쓰지 않는다.

## 남은 검증

- 1~5GB 실제 영상 및 느리거나 불안정한 네트워크의 재개 성능.
- 모바일 파일 선택, 재생·Seek 및 화면 검증.
- 실제 처리 진행률, 완료 결과 다운로드 및 다운로드 도중 TTL/삭제 경합.
- 업로드 생성 요청의 응답이 유실되는 상황의 중복 작업 방지.
